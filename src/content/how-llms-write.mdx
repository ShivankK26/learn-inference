<TLDR>
  An LLM never writes a whole answer at once. It first **reads your entire prompt in one go** (*prefill*), then
  **writes the reply one token at a time** (*decode*). Each decode step produces a score for every token in its
  vocabulary, turns those scores into probabilities, and picks one. Those two phases behave completely differently, and
  that difference shapes the whole field.
</TLDR>

## LLMs are autoregressive

The book’s one-sentence definition: an LLM is an **autoregressive token generation model**. It generates new tokens
**one at a time**, and each new token is based on **every token before it**. Everything in this lesson follows from
that: the model can’t write token 50 until it has written token 49, because token 49 is part of the input for token 50.

## Step 0: text becomes tokens

Models don’t see letters or words. They see **tokens**, the atomic units of language models. A token is a **number**
that stands for a chunk of text. Modern LLMs use **subword tokenization**: each token is a whole word or a fraction of
one. The book’s Figure 2.5 shows the pattern: a common word or a punctuation mark gets a single token, while a less
common word gets split into several.

<Tokenizer />

Some important facts about tokenization:

- **It doesn’t involve a neural network.** A **tokenizer** is a simple, deterministic mapping between strings and
  their token numbers, in both directions.
- The complete mapping is the model’s **vocabulary**. Most models have **over 100,000 tokens** in theirs.
- Vocabularies and tokenizers **differ from model to model**. You can’t feed one model’s tokens to another.
- Newer models tend to use **more efficient** tokenizers. **The fewer tokens it takes to represent a request and its
  answer, the faster the end-to-end inference**, because every output token costs a full decode step.
- In other modalities the idea stretches: a speech-synthesis model’s vocabulary is expanded so that some tokens
  represent pieces of **audio** instead of text.

<Worked title="Estimating tokens from words">
  The book’s glossary gives a rule of thumb for English: roughly **4 tokens for every 3 words**.

  1. A 750-word blog post ≈ 750 × 4 ÷ 3 = **1,000 tokens**.
  2. If a model decodes at 50 tokens per second, writing that post takes about 1,000 ÷ 50 = **20 seconds**.
  3. A tokenizer that needed 10% fewer tokens for the same text would cut that to about 18 seconds, with no change to
     the model at all.
</Worked>

<Note kind="beyond">
  **Where vocabularies come from.** Most modern tokenizers are built with a method called byte-pair encoding (BPE):
  start with single characters (or bytes), then repeatedly merge the most frequent adjacent pair in a large body of text
  into a new token, until the vocabulary reaches the target size. Frequent words end up as single tokens; rare words are
  spelled out from smaller pieces. That’s why the split in the demo above depends on how common a word is.
</Note>

## The sequences in a request, and the context window

Inference involves two or three sequences of tokens:

1. **Input sequence**: the prompt, the chat history, any retrieved context, function definitions, and anything else
   passed in.
2. **Reasoning sequence** (optional): for reasoning models, an intermediate output the model writes to “think” before
   answering.
3. **Output sequence**: the response.

All of these combined must fit inside the model’s **context window**: the total number of tokens it can process *and*
generate for one request. A request can also cap the output with a **`max_tokens`** argument.

<Worked title="A context window budget">
  A model has a context window of 32,000 tokens. You send a 30,000-token prompt, and the model spends 1,500 tokens
  reasoning.

  1. Tokens already used: 30,000 + 1,500 = **31,500**.
  2. Room left for the visible answer: 32,000 − 31,500 = **500 tokens**, and less if `max_tokens` is set lower.
  3. The reasoning tokens are generated by decode just like the answer, so they cost the same time per token even if
     the user never sees them.
</Worked>

### Chat templates

The input sequence is technically a single string, but LLMs are trained to accept structured input: **multi-turn chats
with roles** (system, user, assistant), **function signatures** for tool calls, and sometimes **images or other
media**. All of that has to be flattened into one sequence. That job belongs to the **chat template**.

Chat templates **differ subtly from model to model**, and the book stresses that they must be **implemented correctly
in the inference engine**. A template that’s slightly off (a missing separator, the wrong special token) won’t crash
anything; the model will just quietly perform worse, which is the most dangerous kind of bug.

<Note kind="beyond">
  Here’s what Llama 3’s template produces for a system prompt plus one user message. The special tokens mark where each
  role starts and ends, and the final header tells the model it’s the assistant’s turn to speak:

  ```text
  <|begin_of_text|><|start_header_id|>system<|end_header_id|>

  You are a helpful assistant.<|eot_id|><|start_header_id|>user<|end_header_id|>

  What is inference?<|eot_id|><|start_header_id|>assistant<|end_header_id|>
  ```

  Another model family uses entirely different markers for the same conversation, which is why the template has to
  match the model exactly.
</Note>

## The two phases: prefill and decode

Tokenizing the input with the chat template applied is **step zero**. Then inference has two primary phases:

- <Compute>Prefill</Compute>: the model processes the **entire input sequence at once**, calculating attention for every
  input token and storing the results in a **KV cache** (next lesson).
- <Memory>Decode</Memory>: the model performs **forward passes** to generate tokens **autoregressively**, one per pass.

<Note kind="beyond">
  **What a forward pass is.** One forward pass means running data through every layer of the network, from the
  embedding layer at the bottom to the output layer at the top. During prefill, that pass carries all the prompt tokens
  together. During decode, each pass carries just the newest token (the KV cache supplies everything the model needs to
  know about the earlier ones). Either way, the pass touches every layer, which means reading every weight in the model.
</Note>

The two phases map onto the two speed numbers users actually feel:

| Metric | What it measures | Mainly set by |
|---|---|---|
| **TTFT** (time to first token) | How long you stare at a blank screen | <Compute>Prefill</Compute> |
| **TPS** (tokens per second) | How fast text streams once it starts | <Memory>Decode</Memory> |

The first output token arrives at the end of prefill, because the same pass that processes the prompt also produces
the scores for the first new token. Every token after that costs one decode pass.

<Analogy>
  Think of a **simultaneous interpreter** handed a speech on paper. First they read the whole page and take notes
  (prefill: all at once). Then they speak the translation word by word, each word depending on everything they’ve said
  so far (decode: one at a time). A longer page means a longer pause before they start; a longer translation means more
  time speaking.
</Analogy>

The book points out that these two pieces, **building the KV cache during prefill** and **generating logits during
decode**, take the overwhelming majority of the time and resources in inference, because they’re the only steps that
run the large neural network. Tokenizing, applying the template, and picking a token from probabilities are cheap by
comparison.

## From vector to token: logits and sampling

Every decode pass must produce a token, but a neural network outputs **vectors**, not tokens. So a few extra steps
happen at the end of each pass.

The **output layer** produces a vector of **logits**: raw, unnormalized scores, with **one number per token in the
vocabulary**. For a 128,000-token vocabulary, that’s 128,000 scores. After normalization, those scores become the
**probability** of each token being the right next one. This is the book’s Figure 2.6: a bar per vocabulary token for
the raw logits, then the same bars converted to percentages that add up to 100%.

The normalization step is called **softmax**:

```
probability of token i  =  e^(logit_i)  ÷  sum over all tokens of e^(logit_j)
```

Raising *e* to each score makes everything positive and exaggerates the gaps between scores; dividing by the total
makes the results add up to 1.

<Worked title="Softmax on three logits">
  Suppose the vocabulary had only three tokens, with logits **mat = 3.2**, **floor = 2.6**, **couch = 2.3**.

  1. Exponentiate: e^3.2 ≈ 24.53, e^2.6 ≈ 13.46, e^2.3 ≈ 9.97.
  2. Add them: 24.53 + 13.46 + 9.97 ≈ 47.97.
  3. Divide each by the total: mat ≈ **51.1%**, floor ≈ **28.1%**, couch ≈ **20.8%**.

  A gap of just 0.9 in logits (3.2 vs 2.3) became a gap of more than 2× in probability.
</Worked>

The output token is then chosen by **weighted random selection** from that probability vector: *mat* is picked about
half the time, *couch* about a fifth of the time. That randomness is why the same prompt can give different answers.

### Steering the choice: temperature, top-k, top-p

You can nudge the selection with **inference arguments**:

- **Temperature** adjusts the **logits themselves, before normalization**: each logit is divided by the temperature.
  Below 1 sharpens the distribution; above 1 flattens it.
- **Top-k** keeps only the **k most likely tokens** after normalization, then **re-normalizes** among them.
- **Top-p** keeps the **smallest set of tokens** (after normalization) whose probabilities **add up to p**, then
  re-normalizes among them.

<Worked title="Temperature, top-k and top-p on the same three tokens">
  Start from the logits above (3.2, 2.6, 2.3).

  1. **Temperature 0.5**: divide by 0.5 → 6.4, 5.2, 4.6. Softmax gives mat ≈ **68.2%**, floor ≈ 20.5%, couch ≈ 11.3%.
     The favorite got more likely.
  2. **Temperature 2**: divide by 2 → 1.6, 1.3, 1.15. Softmax gives mat ≈ **42.0%**, floor ≈ 31.1%, couch ≈ 26.8%.
     The choice got more random.
  3. **Top-k = 1**: only *mat* survives, at 100%. Always the same answer.
  4. **Top-p = 0.7** (at temperature 1): mat alone is 51.1%, short of 70%; adding floor brings it to 79.2%, which
     reaches 70%. So *mat* and *floor* survive and are re-normalized to about **64.5%** and **35.5%**. *Couch* can no longer
     be picked.
</Worked>

Lower temperature, top-k, or top-p all make output **more predictable**, because the model is limited to highly likely
tokens. Setting **temperature to 0** or **top-k to 1** makes selection **deterministic**: the highest-probability
token is always chosen (this is called *greedy* decoding).

<Note kind="beyond">
  Mathematically, dividing by a temperature of exactly 0 is undefined, so engines special-case it and simply take the
  top token. Also note that “deterministic token choice” doesn’t always mean bit-identical outputs across runs on real
  servers: tiny numerical differences from batching and hardware can occasionally flip a near-tie.
</Note>

### Structured output and logit biasing

Sometimes the output must follow a strict format, such as JSON that matches a schema. Here, prompting alone isn’t
reliable enough, so engines use additional tools like **logit biasing** to steer generation. These adjustments are
applied **after each forward pass**, before a token is picked. The book notes that they underpin important abilities
like **tool use**, and that implementing them correctly is **essential** for high-quality inference.

<Note kind="beyond">
  The simplest form of constraint works like this: at each step, the engine works out which tokens would still produce
  valid output, and sets the logits of every other token to negative infinity. After softmax those tokens have
  probability exactly zero. For example, if the output so far is `{"name": ` and the schema says the value must be a
  string, only tokens that begin with a quote mark remain possible.
</Note>

### When does it stop?

This loop (produce logits, pick a token, append it, run the next pass) continues until the model generates the **stop
token**, a special vocabulary entry that means “end of output.” Generation also ends early if the **context window**
fills up or the **`max_tokens`** limit is reached.

### The whole loop, start to finish

1. Apply the **chat template** and **tokenize** the input.
2. **Prefill**: process all input tokens at once, build the KV cache, and produce logits for the first output token.
3. **Sample** a token from those logits (temperature, top-k, top-p, any logit biasing).
4. **Decode**: run a forward pass on the new token, using the KV cache for everything before it, to get the next logits.
5. Repeat steps 3–4 until a stop token, `max_tokens`, or the context window ends it.
6. **Detokenize**: turn the token numbers back into text (streamed to the user as it goes).

## Reading a model’s architecture

Every LLM on **Hugging Face**, the largest repository of open models, ships with a **`config.json`**: a few dozen lines
describing the model’s architecture.

A model’s **architecture** is the set of decisions made during training about the nature and shape of each component.
Within a single architecture there can be:

- **Multiple sizes**: the same design at different parameter counts, like Llama 8B and 70B.
- **Multiple variants**: the “base” and “instruct” versions of a model share an architecture.
- **Unlimited fine-tunes**: methods like **LoRA** (low-rank adaptation) change a model’s *behavior*, not its
  architecture.

Why this matters for inference: architectures determine **runtime and engine support**. If you have a highly optimized
deployment of one architecture, you can deploy **any other variant of that architecture** and get the same performance
improvements for free.

The architecture name is one of the first lines in the config. Take `Qwen3MoeForCausalLM`:

- **Qwen**: the model family, i.e. the brand name.
- **3**: the major version of the architecture within that family.
- **Moe**: a **Mixture of Experts** model (next lesson).
- **CausalLM**: a **causal language model**.

A causal language model predicts the **next** token from the **previous** ones. The contrast is a **masked language
model**, which fills in a blank using the tokens on **both** sides. Every generative LLM today is a causal language
model.

Beyond the name, `config.json` describes the nature and **dimensions** of the layers inside the model and of the
vectors that flow through them during inference.

<Note kind="beyond">
  Here are some of the fields in Qwen3-235B-A22B’s config (the real file has more). You’ll meet most of them in the next
  lesson:

  ```json
  {
    "architectures": ["Qwen3MoeForCausalLM"],
    "hidden_size": 4096,
    "num_hidden_layers": 94,
    "num_attention_heads": 64,
    "num_key_value_heads": 4,
    "num_experts": 128,
    "num_experts_per_tok": 8,
    "vocab_size": 151936
  }
  ```

  Read it as: every token is a 4,096-number vector; there are 94 transformer blocks; attention uses 64 query heads that
  share 4 key/value heads; each block has 128 experts, of which 8 are used per token; and the output layer produces
  151,936 logits, one per vocabulary entry.
</Note>

<KeyPoints>
- LLMs are **autoregressive**: one token at a time, each based on every token before it.
- A **tokenizer** (not a neural network) maps text to tokens via a **vocabulary** of 100,000+ entries. Fewer tokens = faster. English ≈ 4 tokens per 3 words.
- Input + reasoning + output must fit the **context window**; `max_tokens` caps the output. **Chat templates** flatten structured chats and must match the model exactly.
- <Compute>Prefill</Compute> processes the whole prompt and builds the KV cache (sets **TTFT**); <Memory>decode</Memory> produces one token per forward pass (sets **TPS**).
- Each pass ends in **logits** (one per vocabulary token) → **softmax** → weighted random pick, shaped by **temperature, top-k, top-p**, and **logit biasing** for structured output.
- `config.json` defines the **architecture**; optimizations carry over to every size, variant, and fine-tune that shares it.
</KeyPoints>
