<TLDR>
  **PyTorch** is the Python toolkit almost everyone uses to build, train and run models. From there, a model reaches
  production in one of a few ways: **compile it with PyTorch**, **export it to ONNX / TensorRT**, or (increasingly
  often) **hand the safetensors weights to an inference engine** like vLLM. Hugging Face’s `transformers` and
  `diffusers` are reference implementations for learning and experimenting, not for production serving.
</TLDR>

## The middle layer of the stack

Deep learning frameworks and libraries are **the bridge between working directly in CUDA and using off-the-shelf
inference engines** like vLLM. They’re used for **both training and inference**, which is part of why they matter so
much: the same code that trained a model is often the starting point for serving it.

Over the past few years, **PyTorch** has emerged as the clear leader at this level of the stack. The book mentions two
other frameworks only briefly, and so will we:

- **TensorFlow**: an end-to-end machine learning platform officially supported by Google. It was prominent in the
  2010s machine learning era but has fallen out of favor today.
- **JAX**: a research project unofficially associated with Google. It presents a simpler interface without as many
  legacy features and operations, but, as its own documentation warns, expect “sharp edges”.

The rest of this lesson is about PyTorch and the technologies around and above it.

## PyTorch

PyTorch is a **Python package for describing tensor operations**. Originally created at Meta and now part of the Linux
Foundation, it’s the **industry-standard technology underlying both training and inference** for generative AI models.

A <Term def="A multi-dimensional grid of numbers with a type (like FP16) and a location (CPU or a specific GPU). Vectors and matrices are tensors with 1 and 2 dimensions.">tensor</Term>
is just a multi-dimensional grid of numbers: a vector is a 1D tensor, a matrix is 2D, and a batch of sequences of token
embeddings is 3D (batch × tokens × dimensions). PyTorch lets you describe math on tensors in ordinary Python, and it
turns that math into kernels on whatever device the tensor lives on.

The book’s author makes a personal point here that captures PyTorch’s appeal. As a lifelong Python programmer who finds
low-level C++ hard going, the author can still write **highly performant inference code in Python, for both CPUs and
GPUs**, with the option to **dip down into CUDA** whenever necessary by plugging in specific kernels. You get Python’s
productivity for most of the code and CUDA’s speed exactly where it counts.

### A neural network in PyTorch

PyTorch can train any kind of neural network. The book shows a basic example adapted from the PyTorch documentation,
which looks like this:

```python
import torch
from torch import nn

class NeuralNetwork(nn.Module):
    def __init__(self):
        super().__init__()
        self.flatten = nn.Flatten()
        self.linear_relu_stack = nn.Sequential(
            nn.Linear(28 * 28, 512),  # linear layer: matmul + bias
            nn.ReLU(),                # activation function
            nn.Linear(512, 512),
            nn.ReLU(),
            nn.Linear(512, 10),
        )

    def forward(self, x):
        x = self.flatten(x)
        return self.linear_relu_stack(x)
```

It’s a very simple network, but you’ll recognize the key pieces from [Neural networks from the ground up](/learn/neural-networks):
**linear layers** (each one a matmul plus a bias) separated by **ReLU activation functions** so the layers don’t
collapse into one. An LLM is, structurally, a much bigger and more elaborate version of the same idea.

<Note kind="beyond">
  By default PyTorch runs in **eager mode**: each line executes immediately, launching its GPU kernels one by one as the
  Python interpreter reaches it. That makes PyTorch easy to write and debug (you can print any tensor at any point), but
  it means every small operation pays Python overhead and a kernel launch, and consecutive operations each read and
  write their data from GPU memory separately. Compilation, below, is largely about removing those costs.
</Note>

### Great for training: autograd

PyTorch automatically computes **gradients for any differentiable function** via its **autograd** module. A gradient
tells you, for every weight, which direction to nudge it to reduce the error. This is what makes PyTorch so powerful
for training: **you define a computation graph, and you get a gradient to train against**, without deriving any
calculus by hand.

<Note kind="beyond">
  During inference you don’t need gradients at all. Wrapping inference code in `torch.inference_mode()` (or the older
  `torch.no_grad()`) tells PyTorch not to record the operations autograd would need, which saves memory and time.
  Serving code almost always does this.
</Note>

### Also great for inference

What makes PyTorch special is that it isn’t just great for training; it’s also **powerful for inference**. It balances
**built-in functions and automatic performance optimizations** with **manual control where you need it**.

The step that transforms a model from training to inference is **compilation**. **`torch.compile`** targets a
**specific GPU** and performs **automatic kernel selection and kernel fusion** (both from
[the previous lesson](/learn/cuda-and-kernels)) to get the best performance out of it.

<Note kind="beyond">
  **How `torch.compile` works, roughly.** Calling `model = torch.compile(model)` doesn’t change anything immediately.
  The first time the model runs, a component called TorchDynamo watches the Python code execute and **captures the
  tensor operations into a graph**. A compiler backend (TorchInductor, by default) then optimizes that graph: it fuses
  runs of small operations into single kernels (on NVIDIA GPUs it generates them in the Triton kernel language) and picks
  library kernels, like cuBLAS matmuls, for the big operations. The compiled version is cached and reused on later
  calls.

  When Dynamo meets Python it can’t turn into a graph (printing a tensor’s value, calling `.item()`, branching on a
  tensor’s contents, some third-party library calls), it inserts a **graph break**: the model gets split into separate
  graphs with ordinary Python running in between, and nothing can be fused across the break. Two modes are worth
  knowing: `mode="reduce-overhead"` uses CUDA graphs to cut kernel launch overhead, and `mode="max-autotune"` benchmarks
  several kernel variants and keeps the fastest. The catch with all of it is time: the first run is slow while
  compilation happens, which matters for cold starts ([Autoscaling](/learn/autoscaling)) unless you cache the compiled
  result.
</Note>

### The limits of `torch.compile` for LLMs

There’s an important catch. **`torch.compile` can’t fuse plugin kernels** like **DeepGEMM**, **FlashAttention**, or your
own custom kernels. It treats them as black boxes: it can fuse the small operations around them, but not into them.
That **limits its usefulness for LLM inference**, where **most of the important kernels are custom**. By the time you’ve
plugged in FlashAttention for attention and specialized kernels for the big matmuls, there’s not much left for the
compiler to improve.

Where `torch.compile` shines instead:

- **Less common model architectures**, where no one has hand-written custom kernels yet.
- **Compiling long sequences of lightweight kernels**, the kind of chain of small ops the widget above shows.

<Note kind="warn">
  When you’re optimizing a model with a **custom or rare architecture**, you may have to **rewrite some functions to be
  more abstract**, especially code that relies on **Python-specific language features**, before compilation succeeds.
  That’s the graph-break problem from the note above: the compiler can only optimize what it can capture.
</Note>

PyTorch alone is a powerful and flexible tool for building high-performance inference services. But there’s a rich
ecosystem on top of it that makes it faster to **implement, compile and execute optimized code for common model
architectures**. The next sections cover how models are stored, how they can be exported, and the libraries you’ll
meet on every model page.

## Model file formats

A trained model is mostly its weights, and those weights have to be stored on disk and loaded onto GPUs. Two formats
matter.

### safetensors (the default)

The dominant file format for serializing model weights is **safetensors**, created by **Hugging Face**. It replaces
generic formats like `.bin`, and it’s **designed specifically for holding model weights**.

- **Why “safe”?** A general-purpose format can **execute arbitrary Python code during deserialization** (loading). A
  malicious model file could run code on your machine the moment you loaded it. **safetensors files only hold tensor
  data, never executable code**, so loading one can’t run anything.
- **Why fast?** Generative AI models have **hundreds of gigabytes of weights**, split across **dozens of safetensors
  files**. The format uses
  <Term def="Letting the operating system treat a file on disk as if it were already in memory, and loading pieces only when they’re actually touched.">memory mapping</Term>
  so the files are loadable **without allocating the full memory up front**, which makes loading weights both **faster and
  safer**.

<Note kind="beyond">
  The generic `.bin` files are typically Python *pickle* files, and unpickling can run any code embedded in the file,
  which is exactly the risk safetensors removes. A safetensors file is deliberately simple: a small header (JSON listing
  each tensor’s name, number type, shape and byte offsets), followed by the raw bytes of the tensors. Because every
  tensor’s location is known up front, a loader can map the file and pull out exactly the pieces it needs, for example
  only the layers assigned to one GPU. Sharded models ship an index file (`model.safetensors.index.json`) that maps each
  tensor to the shard that contains it.
</Note>

<Worked title="How big is a model on disk?">
  Take a 70B-parameter model stored in BF16 (2 bytes per parameter).

  1. **Total size**: 70 billion × 2 bytes = **140 GB** of weights.
  2. **Sharding**: models on Hugging Face are commonly split into shards of a few gigabytes each. At about 5 GB per
     shard, that’s roughly **28–30 files**.
  3. **Why it matters for inference**: those 140 GB have to travel from storage to GPU memory every time a new replica
     starts. That’s one of the biggest pieces of a cold start ([Autoscaling](/learn/autoscaling)), and it’s why fast,
     memory-mapped loading is worth so much.
  4. **Quantized**: the same model in FP8 is about 70 GB, and in a 4-bit format roughly 35–40 GB
     ([Quantization](/learn/quantization)), which is less to store, less to load, and less to read on every decode step.
</Worked>

### ONNX (weights + the recipe)

**ONNX** (Open Neural Network Exchange) is another leading format. It stores the weights **along with an execution
graph** for the model. The difference in one line: **safetensors separates the weights from the architecture; ONNX
bundles them together.**

ONNX files are **highly portable**. With deep integration into PyTorch and support for multiple hardware options,
ONNX is a great alternative to safetensors **when you want to store model graphs, not just weights**.

<Analogy>
  **safetensors** is a box of pre-measured ingredients: safe, easy to open, but you bring your own recipe (the model
  code, from PyTorch or an inference engine). **ONNX** is a meal kit: the ingredients *and* the recipe card, packed
  together so any kitchen that can read the card can cook it.
</Analogy>

## ONNX Runtime and TensorRT

**ONNX Runtime** and **TensorRT** are high-performance inference runtimes. PyTorch models can be **exported to the ONNX
format**, which **ONNX Runtime can execute directly** or **TensorRT can compile into a highly optimized engine**.

| | ONNX Runtime | TensorRT |
|---|---|---|
| **Who makes it** | Open source, associated with the Linux Foundation | NVIDIA, a mix of proprietary and open components |
| **PyTorch integration** | First-class exporter in the PyTorch ecosystem | Integrated with PyTorch via Torch-TensorRT |
| **Hardware** | Supports many types of GPUs | NVIDIA GPUs only |

In short, **ONNX Runtime is an open community standard, while TensorRT is specific to NVIDIA GPUs** (and, like
TensorRT-LLM later, gets its edge from being specific).

### The export problem

The export process looks somewhat like Torch compilation: PyTorch code gets captured and converted into a graph.
However, these standards **don’t support every data structure, type and operation within PyTorch**. The export
process can identify these issues in your PyTorch code, but this **gets tricky with more complex models**.

The book’s example is **DeepSeek V3**, which introduced **Multi-Latent Attention (MLA)**
([Making attention faster](/learn/faster-attention)). MLA, as implemented in PyTorch, is **difficult to export**. At the
same time, the rest of the transformer architecture is **simple enough that hand-fusing its kernels is feasible**. So
for a model like this, the export route is painful and the alternative (writing and fusing kernels directly, or using
an engine that already has) is practical.

### Where the industry is heading

It’s increasingly popular to **skip the export step entirely**: go **directly from PyTorch to an inference engine** like
vLLM or TensorRT-LLM for models those engines support, **bypassing the intermediate representation** and exporting the
weights only, as safetensors.

ONNX Runtime and TensorRT are still widely used, **TensorRT especially for its strong out-of-the-box runtime for image
and video models** ([Serving image & video models](/learn/serving-images-video)). But the book describes the industry as
**bifurcating**: the **control** of handwritten PyTorch code on one side, and the **convenience** of prebuilt inference
engines on the other.

| Path to production | What you ship | Good for |
|---|---|---|
| Handwritten PyTorch + `torch.compile` + plugin kernels | Your own model code + weights | Unusual architectures, maximum control |
| PyTorch → ONNX → ONNX Runtime / TensorRT | A graph with weights (or a compiled engine) | Portable graphs; TensorRT is strong for image and video models |
| safetensors weights → inference engine | Weights only; the engine brings the architecture | Popular LLM architectures, the fastest route to high performance |

## Transformers and Diffusers

Hugging Face’s **`transformers`** and **`diffusers`** libraries are built on PyTorch, but they are **not designed to run
large-scale production inference**. Instead, they offer **reference implementations** of models for inference
engineers to learn from and adapt: clear, readable code for each architecture, written for correctness rather than
peak speed.

They’re toolboxes for tinkering, but they include essential information and utilities:

- The **`config.json`** that ships with models implemented for these libraries holds essential information about the
  model’s architecture ([How an LLM writes](/learn/how-llms-write) shows how to read it).
- Their **utilities for Hugging Face operations**, like downloading model weights, are **widely used**, even in
  production systems that never run `transformers` for inference.
- You’ll find **`transformers` or `diffusers` sample code in the model card** for most popular open models on Hugging
  Face. It’s great for understanding the **exact input and output spec** of a model, and for running local inference
  and notebooks.

<Note kind="beyond">
  Model-card sample code usually looks something like this. Notice that it applies the model’s **chat template** for
  you, the step from Chapter 2 that’s easy to get subtly wrong:

  ```python
  from transformers import AutoModelForCausalLM, AutoTokenizer

  name = "Qwen/Qwen3-8B"
  tok = AutoTokenizer.from_pretrained(name)
  model = AutoModelForCausalLM.from_pretrained(name, torch_dtype="auto", device_map="auto")

  messages = [{"role": "user", "content": "Explain the KV cache in one sentence."}]
  inputs = tok.apply_chat_template(messages, add_generation_prompt=True, return_tensors="pt").to(model.device)
  out = model.generate(inputs, max_new_tokens=100)
  print(tok.decode(out[0][inputs.shape[-1]:], skip_special_tokens=True))
  ```

  Perfect for checking what a model expects and produces. But `generate` here serves one request at a time, with none
  of the continuous batching, paged KV cache management or custom kernels an inference engine adds.
</Note>

<Note kind="warn">
  For production, don’t serve straight from `transformers` or `diffusers`. Either **write and compile PyTorch code
  directly**, or use a **production-ready inference engine** ([next lesson](/learn/inference-engines)).
</Note>

<KeyPoints>
- Frameworks bridge raw CUDA and inference engines, and serve **both training and inference**. **PyTorch** leads;
  TensorFlow has faded; JAX has sharp edges.
- PyTorch describes **tensor operations** in Python, with the option to plug in CUDA kernels where it counts.
  **Autograd** makes training easy.
- **`torch.compile`** targets a specific GPU and does **kernel selection and fusion**, but **can’t fuse plugin kernels**
  (FlashAttention, DeepGEMM, custom), which limits it for LLMs. It shines on rare architectures and long chains of small
  kernels. Python-specific code may need rewriting.
- **safetensors**: weights only, no executable code, memory-mapped, split across many files; the default.
  **ONNX**: weights plus the execution graph; very portable.
- **ONNX Runtime** (open, many GPUs) and **TensorRT** (NVIDIA only, highly optimized) run exported models, but not
  everything exports cleanly (e.g. DeepSeek’s MLA).
- The industry is **bifurcating**: handwritten PyTorch for control, or weights straight into an inference engine for
  convenience. TensorRT stays strong for image and video.
- **`transformers` / `diffusers`**: reference implementations, `config.json`, download utilities and model-card sample
  code. Great for learning, not for production serving.
</KeyPoints>
