## Testing before you deploy

Chapter 4 covered [benchmarking](/learn/benchmarking) a single replica while configuring the engine. Before deploying,
the book says you also need to test the **whole system, end to end**. There are three strategies:

- **Manual testing**: writing scripts (or clicking buttons) to send synthetic traffic to an inference service.
- **Load testing**: automatically sending a large volume of traffic to test the system’s ability to **scale** and
  **maintain performance** under pressure.
- **Shadow traffic**: **copying live traffic** to a test deployment to measure performance under real-world conditions.

Each catches different problems:

| Strategy | What it’s good at catching |
|---|---|
| **Manual testing** | Broken outputs, wrong formats, misconfigured endpoints: does it work at all? |
| **Load testing** | Throughput limits, queue buildup, autoscaling behavior, and latency under heavy load |
| **Shadow traffic** | Surprises from **real** sequence shapes and topics that synthetic tests don’t produce |

<Note kind="beyond">
  **How shadowing works.** A copy of each real request is sent to the new deployment in the background; users still get
  their answers from the current deployment, and the shadow’s responses are thrown away after you record their latency
  and, where useful, compare their outputs. Because shadowing duplicates real user data, it falls under the same privacy
  and retention rules as production traffic.
</Note>

**Testing inference is expensive.** It takes engineering time to configure tests and measure results, and it takes
GPUs to run inference on the test traffic. To a degree that’s the cost of doing business, but the book says to think
carefully about minimizing it. Its example: start by shadowing a **random sample** of production traffic, followed by a
**shorter-duration** load test.

<Worked title="What sampling saves on a shadow test">

1. Production serves **2 million requests a day** on **40 GPUs**.
2. Shadowing **100%** of traffic for a **week** needs roughly another 40 GPUs for 7 days: **6,720 GPU-hours**.
3. Shadowing a **10%** random sample for **2 days** needs about 4 GPUs for 48 hours: **192 GPU-hours**, about 3% of
   the cost, and 400,000 real requests is still a large, realistic sample.
4. A short load test afterwards then checks the one thing a small sample can’t: behavior at full volume.

</Worked>

<Note kind="tip">
  AI product usage generally fluctuates on **daily and weekly cycles**. A test run on a quiet Sunday night can look very
  different from Monday at noon, so keep the calendar in mind when you plan tests and read their results.
</Note>

## Deploying without downtime

Once you’re confident in the updated system’s performance and stability, it’s time to deploy to production, using
**high-availability** strategies to avoid downtime.

**Blue-green deployment** is the traditional design. There are two identical environments: the original **blue**
deployment and a new **green** deployment running the updated service. Once green is ready, **the full traffic load cuts
over** from blue to green, with blue staying ready for rollback in case of issues.

The book explains why blue-green is **not well suited to large-scale inference**: the same GPU capacity and cost issues
that make large-scale testing difficult. If blue uses **100 GPUs**, green needs **another 100 GPUs** before traffic can
cut over. At inference scale, you may not even be able to get the second 100 GPUs.

**Canary deployments** get similar benefits with far lower GPU overhead. The name comes from the canaries once used to
detect gas in coal mines: a canary deployment **catches errors before they affect large numbers of users**. It’s a
four-step process:

1. **Build** a new deployment of the inference service and get it ready to handle incoming requests.
2. **Direct a small percentage** of incoming live traffic to the new service.
3. **Monitor** the new service and make sure it handles traffic correctly. **Revert** if there are any issues.
4. **Gradually increase** traffic, while monitoring for issues, until the new deployment handles **100%** of traffic.

The book’s Figure 7.13 shows traffic shifting over iteratively, so an issue surfaces while only a slice of users is on
the new version.

<CanaryDeploy />

Canary deployments can be rolled out **quickly**, with just a few minutes of traffic ramp, or **slowly** to ensure
stability at each stage. And with autoscaling, they **don’t increase cost much at scale**, because reducing traffic to the
old production system causes it to scale down some replicas.

<Worked title="GPU overhead and blast radius: blue-green vs. canary">

The current deployment runs on **100 GPUs**.

1. **Blue-green:** green must be fully built before cutover, so you briefly run **200 GPUs**. If green has a bug that
   testing missed, it hits **100%** of users the moment traffic cuts over (until you roll back).
2. **Canary at 5%:** the new deployment needs only about **5 GPUs**' worth of capacity. As 5% of traffic leaves the old
   deployment, autoscaling trims it toward **95 GPUs**, so the total stays near **100**.
3. **Ramping 5% → 25% → 50% → 100%:** at every step the new side grows and the old side shrinks by about the same
   amount. A bug found at the 5% step affected only **5%** of users, for only as long as that step lasted.

</Worked>

<Note kind="warn">
  With autoscaling, a new deployment with no traffic defaults to its **minimum** number of replicas. The book’s warning:
  throughout the canary process, make sure the new deployment has **enough active replicas** to handle the traffic you’re
  sending it. Otherwise users see a **latency spike** as their requests queue while autoscaling catches up. Pre-scale the
  new side before each traffic step.
</Note>

<Note kind="beyond">
  **What to watch at each canary step.** Compare the new deployment against the old one on the same metrics: error rates
  (especially 5XX responses), latency percentiles (P99 time to first token and inter-token latency, not just averages),
  and output quality, whether through automated checks or eval spot checks. Many teams automate the rollback: if the
  canary’s error rate or P99 latency crosses a threshold, traffic shifts back without waiting for a human. And make at
  least one step span a busy period, since daily cycles mean a canary that only saw quiet traffic hasn’t really been
  tested.
</Note>

## Estimating cost

Switching from consuming tokens through a public API to running your own inference on dedicated GPUs requires changing
how you think about cost.

**Cost on public APIs is simple**: a price per million tokens times the number of tokens you use. There are a couple of
variables, such as **cache hits vs. cache misses** for input tokens and **discounts** for high-volume users, but cost
remains a **linear function of usage**. Double the tokens, double the bill.

One motivation for investing in inference engineering is to **take control of your unit economics** and escape
per-token pricing. But the book calls it a difficult mental transition, because the blessing and curse of dedicated
inference is that **cost is now a function of many variables**. That’s good because it gives you control, and hard
because it makes estimation difficult. The factors include:

- **Batch sizing**: is the deployment optimized for **latency** with low batch sizes, or for **throughput** with high
  batch sizes?
- **Traffic patterns**: is traffic consistently **saturating** active GPUs, or is capacity going spare?
- **Sequence lengths**: how many input and output tokens do requests have, both **on average** and in **outlier** cases?

Given this complexity, and the difference in price between input and output tokens, the book advises that it’s
generally more productive to **convert your token price into a total cost and compare that to dedicated**, instead of
trying to reverse-engineer a per-token price from what you pay for GPUs. The book gives one equation for each side
(Figures 7.14 and 7.15, not reproduced in this course). *Reconstructed in plain terms:*

```text
API total cost  ≈ uncached input tokens × input price
                + cached input tokens   × cached input price
                + output tokens         × output price        (prices per million tokens)

Dedicated total ≈ Σ over instance types: number of GPUs × price per GPU-hour × hours in the period
```

<Worked title="Comparing a week of API spend with dedicated GPUs">

All prices and throughput figures are illustrative.

1. **Usage per week:** 3 billion input tokens (a third of them cache hits) and 600 million output tokens.
2. **API total:** 2,000M uncached × $0.60 + 1,000M cached × $0.15 + 600M output × $2.40 per million
   = $1,200 + $150 + $1,440 = **$2,790 per week**.
3. **Dedicated sizing:** 600M output tokens over a week (604,800 s) is about **1,000 output tokens per second** on
   average. Traffic isn’t flat; say the busiest hours run at **3×** average, so you need about **3,000 tokens per
   second** at peak, plus the prefill work for all that input.
4. If one 8-GPU node sustains that at your latency SLA, you need **one node, plus a second for redundancy**: 16 GPUs.
5. **Dedicated total:** 16 GPUs × $3.00 per GPU-hour × 168 hours = **$8,064 per week**, before engineering time.
6. **Verdict at this scale:** the API wins by far. Dedicated only pulls ahead when usage grows enough to keep those GPUs
   busy. At 5× this usage the API bill would be about $13,950, while the same two nodes (if they can absorb it) still
   cost about $8,064.

</Worked>

<ApiVsDedicated />

<Note kind="beyond">
  **Why a “dedicated price per million tokens” is slippery.** You *can* compute one: price per hour ÷ (tokens per
  second × 3,600) × 1,000,000. A node costing $24 an hour that produces 10,000 tokens per second makes 36 million tokens
  an hour, about **$0.67 per million**, but only if it’s saturated every hour. At 30% average utilization the effective
  price is about **$2.22 per million**. It also changes with batch size and the mix of input and output tokens. That
  sensitivity is exactly why the book says to compare **totals** over a long window instead.
</Note>

Two more rules from the book:

- **Use a long time horizon**, ideally **at least a week**, to smooth out variations in usage (weekends, launches, daily
  cycles).
- **Include engineering time.** The time spent building and maintaining inference systems is justified by increased
  reliability, security, and control, but it should be added to GPU costs to form a complete picture of the **total cost
  of ownership** (<Term def="Total cost of ownership: everything it really costs to run something, including hardware and the people who build and maintain it.">TCO</Term>)
  for inference.

## Observability: watching it run

Inference is mission-critical, so it must be monitored like any other mission-critical component, with **alerting,
logs, and observability** built at the right level of abstraction. The first question is what to monitor. The book’s
list:

| Metric | What it tells you |
|---|---|
| **Total volume** | The number of requests the deployment is receiving |
| **Request and response sizes** | The input and output sequence lengths being processed |
| **Response codes** | Counts of 2XX (success), 4XX (client error), and 5XX (server error) responses |
| **Latency** | Time to first token, tokens per second, and end-to-end latency at P50, P90, and P99 |
| **Replica count** | Instances actively serving traffic, and instances still starting up |
| **Utilization** | Usage across CPU, host memory, GPU, and GPU memory |
| **Queue depth** | For asynchronous traffic, the number of requests enqueued and waiting |

These metrics are **interdependent**. The book’s example: a spike in latency could come from **request volume**, but it
could also come from **long input sequences**. Seeing the metrics together lets inference engineers understand not only
*what* is happening but *why*.

<Worked title="Diagnosing a latency spike with metrics side by side">

1. **Alert:** at 2 p.m., P99 time to first token doubles from 400 ms to 800 ms.
2. **Volume:** flat. So it isn’t simply more users.
3. **Request sizes:** P99 input length jumped from 4,000 to 40,000 tokens. Someone is sending very long prompts.
4. **Utilization:** GPU compute is pinned on a few replicas while others are fairly idle. The long prompts are clustering
   on some replicas and creating heavy <Compute>prefill</Compute> work there.
5. **Replica count:** unchanged, because traffic-based autoscaling counts *requests*, and the number of requests didn’t
   change.
6. **Diagnosis and fixes:** prefill-heavy requests are hurting their neighbors. Options from earlier lessons: route by
   sequence length, use chunked prefill so long prompts don’t block others, and let utilization signals trigger
   scaling. No single metric would have told you all of that.

</Worked>

When things go wrong, inference engineers need information to fix issues. **Logs** deliver that information in real
time: both **server logs** (what the service is doing) and **audit logs** (showing changes made to an inference service:
who changed what, and when).

And observability **cannot be siloed**. The book says to build it with deep integration into existing observability and
alerting tools, such as **Grafana, Datadog, PagerDuty, and Sentry**, to put inference information in context with the
rest of the application.

<Note kind="beyond">
  **SLA, SLO, SLI.** An *SLA* (service level agreement) is the external promise, like “P95 time to first token under 500
  ms, 99.9% uptime,” often with financial penalties. An *SLO* (service level objective) is your stricter internal target,
  say 400 ms, so you get warned well before breaking the promise. An *SLI* (service level indicator) is the actual
  measurement you compare against both. Alerts work best on user-facing symptoms like P99 latency and 5XX rates, with
  the other metrics in the table used to find the cause.
</Note>

## The client side

Inference engineering draws on many technologies, from CUDA to Kubernetes. But the book singles out one critical area
that’s often overlooked when optimizing for latency and building for scale: **client code**. There are two sides to
every call:

- The **client**: the browser, agent, or application making a request to the inference service.
- The **server**: the inference service that handles the request and returns the model’s results.

The industry standard for client code is the **OpenAI SDK**, which supports a wide range of compatible providers in
addition to OpenAI’s own models. Popular AI engineering frameworks and libraries like **LangChain, Vercel AI SDK,
LiteLLM, and LlamaIndex**, and dozens more, can also act as clients. Whether you use an existing library or your own
code, there’s potential for **latency overhead** or **throughput bottlenecks** on the client side. And real-time apps may
need a protocol other than plain HTTP, like **WebSockets**, to keep a continuous connection open.

The book’s Figure 7.16 makes the key point: **on-server inference time is just a fraction of the end-to-end latency for a
given request.** Network travel, connection setup, and client processing surround it.

<RequestTimeline />

### Re-use your connections

Depending on the client’s internet connection and the protocol used, **establishing a session** between client and server
takes **a few dozen milliseconds**.

In a high-performance system with a **300 ms P95** end-to-end latency SLA, the book notes that a
<Term def="The back-and-forth a client and server do to set up an encrypted connection before any real data flows.">TLS handshake</Term>
costs **at least 10%** of that latency budget before inference even starts. Later requests from the same client should
save that time by **re-using the existing session**. Session re-use is not a new idea, and tools like the OpenAI SDK do it
silently under the hood. But when you build your own client, for example for non-standard modalities, follow the same
best practice.

<Worked title="What a fresh connection costs">

1. The user is **30 ms** round trip from your server.
2. A new connection needs a transport handshake (about **one round trip**) and then a TLS handshake (about **one more**
   with modern TLS): roughly **60 ms** before the request is even sent.
3. Against a **300 ms** P95 budget, that’s **20%** gone. Even a very close user pays the book’s “at least 10%.”
4. A re-used session skips both handshakes: the request goes out immediately on the already-open connection.

</Worked>

<Note kind="beyond">
  **How clients re-use sessions.** HTTP clients keep connections open between requests (*keep-alive*) and hold a
  *pool* of open connections to reuse. Newer versions of HTTP can also carry many requests over one connection at the
  same time. The common mistake in hand-written clients is creating a new client object, and therefore a new
  connection, for every request.
</Note>

### Asynchronous inference

Some systems are built for **throughput, not latency**. Use cases like **bulk document processing** and **embedding an
entire corpus** aren’t latency-sensitive, so it makes sense to switch to **asynchronous jobs**, a “fire and forget”
approach:

- Ordinary **synchronous** requests have a **timeout**, generally a few minutes, after which the request fails.
- **Asynchronous** jobs are **acknowledged immediately**. Later, the result is returned to a
  <Term def="A URL you give the service ahead of time; it calls that URL to hand you the result when the job is done.">webhook</Term>
  supplied in the original request.

Asynchronous jobs still have time limits, but they’re usually measured in **hours, not minutes**. Combined with strong
**server-side queueing**, asynchronous requests make high-throughput, latency-insensitive systems more robust and
efficient: the server can work through the queue at full batch sizes, at its own pace, instead of juggling timeouts.

<Worked title="The life of an asynchronous job">

1. Your system submits “summarize these 50,000 documents” along with a webhook URL.
2. The service **immediately replies** “accepted, job 123”. Nothing is held open, so no timeout can fire.
3. The job waits in the server-side **queue** and runs as capacity allows, in large, efficient batches.
4. Hours later, when it finishes, the service **calls your webhook** with the results (or with where to fetch them).
5. If it runs past its limit, which is usually hours, it fails cleanly instead of your client hanging for minutes and
   timing out.

</Worked>

<Note kind="beyond">
  **Two habits for async systems.** Make submissions *idempotent*, for example with a unique job key, so a client that
  retries after a network hiccup doesn’t start the same expensive job twice. And verify incoming webhook calls (commonly
  with a signature) so nobody else can post fake results to your endpoint.
</Note>

### Streaming, WebSockets, and gRPC

**Streaming makes applications feel instant.** Tick the streaming box in the timeline above: the user starts reading after
prefill instead of waiting for the last token. For **language models**, streaming text output over **HTTP** is
sufficient.

<Note kind="beyond">
  **How text streaming over HTTP works.** OpenAI-compatible APIs stream by keeping the HTTP response open and sending
  each new chunk of tokens as a small event the moment it’s generated (a format called *server-sent events*). It’s
  one-directional, server to client, which is all a chat reply needs.
</Note>

But for other modalities, especially **live voice and video**, both the **input and output** streams need to carry much
more data, continuously. The book’s Figure 7.17 contrasts one-time HTTP requests and responses, a good fit for text chat,
with the continuous streaming that live media needs. The two most common **bi-directional** streaming protocols are:

- **WebSockets**: for streaming use cases where strong schema enforcement is **not** required.
- **gRPC**: for well-defined **service-to-service** communication.

**WebSockets** (Figure 7.18) establish a continuous connection that’s useful for transmitting **unstructured, real-time
data like audio**, where the server receiving it parses and processes it downstream. With WebSockets, a server supports up
to a **fixed, developer-configurable number of clients**; once that concurrency is reached, new connections **can’t be
established** and must wait until a slot frees up or another replica scales up. (That’s the same concurrency-target logic
from the [autoscaling lesson](/learn/autoscaling), applied to open connections.)

**gRPC** (Figure 7.19) also supports bi-directional streaming, but for **structured** data. Requests sent via gRPC must
follow a **predefined schema**, which takes away the work of parsing free-form input. The book notes that this extra
validation layer makes gRPC **slightly slower than WebSockets**.

| Protocol | Best for | Key property |
|---|---|---|
| **HTTP (streamed response)** | Text chat from an LLM | Simple; the server streams, the client listens |
| **WebSockets** | Unstructured real-time data, like live audio | Continuous two-way connection; fixed number of clients per server |
| **gRPC** | Structured service-to-service calls | Two-way streaming with an enforced schema; slightly slower than WebSockets |

<Note kind="beyond">
  **Under the hood of gRPC.** gRPC runs over HTTP/2 and encodes messages with *Protocol Buffers*, a compact binary
  format defined by a schema that both sides share. That shared schema is what enforces structure, and it’s why gRPC is
  popular between internal services, such as one model in a pipeline calling the next.
</Note>

- Test end to end with **manual tests, load tests, and shadow traffic**; control test cost by sampling traffic and
